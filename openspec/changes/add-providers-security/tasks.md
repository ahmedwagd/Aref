# Tasks

Four PR slices inside one change, sequenced by dependency: 1 → 2 → 3 → 4, then one integration group. A slice starts only when the previous one's group is fully checked. Every task names the requirement IDs it serves — the aggregate gates in group 5 say why they serve none — and carries one binary check; a task is done when that check passes, not when the code exists.

Resolved decisions are cited, never restated: `G-09`, `G-13`, `G-19`, `G-20`, `G-27` (`docs/SRS.md` §9; `design.md` §1.1). Where a task touches one, it cites the ID and leaves the rule in its source. The five decisions settled on 2026-10-22 are the exception: each is stated in the task that rests on it, because a `code` string, a parse rule, a mask boundary, a refusal marker, and a missing sink cannot be checked against a citation alone.

Citation note: selection's no-egress guarantee is cited to `G-19` and to the `providers` requirement "Selection order is configured and network-free" (`FR-312`). `G-12` is `Open` (SRS line 1109, the settings inventory); it is cited only as the reason no settings command is in this change, never as the source of the no-egress rule.

## Settled decisions (2026-10-22)

Approved by the product owner on 2026-10-22. None of these is a gate any more: the tasks below are written against the settled choice, and reversing one is a new change, not a re-read of this file. `D-1`–`D-5` are this file's IDs; `docs/design/DESIGN.md`'s `D-01`–`D-09` are a separate namespace — the zero padding is the difference, not a typo.

- **`D-1` — `E_INPUT_EMPTY` with `params.field` is the provider-field validation code** (`docs/SRS.md` §7 line 932; `design.md` §4.6, risk `R-7`). No `E_INPUT_INVALID` row is added: the catalog holds one input-validation code, and the field name rides in `params` so the UI can attach the message to the right input. 1.6, 1.7 and 3.17 are written against it. `code` stays a one-way door (`R-2`) for any later change.
- **`D-2` — `Retry-After` is delta-seconds only** (`design.md` §6.3). An HTTP-date value is unusable, so the computed curve applies; no `httpdate` dependency and no date-parsing branch. 3.6's `resolve` and 3.7 are written against it.
- **`D-3` — no logging backend in slices 1–3** (`design.md` §3.4, §13 item 4). `log::` records exist carrying counts, ids, durations and codes only, and reach no sink. 3.18 is written against it: a backend, when a later change picks one, adds a sink and a redaction test at that sink, and changes no call site.
- **`D-4` — the mask boundary is four or fewer for mask-only, five or more for the tail** (owner, 2026-10-22; `design.md` §5.3/§6.5 now states the predicate as `s.chars().count() ≤ VISIBLE_TAIL`). `VISIBLE_TAIL = 4` is unchanged: at five characters or more the preview is `MASK_WIDTH` mask characters followed by the last four; at four or fewer it is `MASK_WIDTH + VISIBLE_TAIL` mask characters and reveals nothing. A four-character secret is therefore never fully revealed, which the earlier `s.chars().count() < VISIBLE_TAIL` reading allowed. No key is rejected for length. 2.6 and 2.13 are written against it.
- **`D-5` — a refusal is a 200 response with `finish_reason: "content_filter"`** (owner, 2026-10-22). It maps to `E_OUTPUT_REJECTED { reason: "refused" }`, and any content it carries is never returned as the rewrite. 3.13 is written against it.

**Alignment.** As of 2026-10-22 the change's artifacts agree: `design.md` §4.6/§5.3/§6.5/§13 items 1, 2, 4 and 7 carry `D-1`, `D-2`, `D-3` and `D-4`; the `key-security` scenarios "The preview shows only the last four characters", "A secret of `VISIBLE_TAIL` characters or fewer shows the mask only" and "The tail appears only from the fifth character" carry the same boundary; and `providers`' requirement text plus the scenario "A protocol-marked refusal is a failed attempt" carry `D-5`. No artifact still holds the earlier `s.chars().count() < VISIBLE_TAIL` reading or an undefined "is a refusal".
